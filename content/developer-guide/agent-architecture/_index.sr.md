LibreAgent је платформски неутрално језгро LibreSCRS картичног агента, од 5.0
објављено као библиотека за себе. Ова страница покрива седамнаест јавних
заглавља од којих се само језгро састоји: `include/LibreSCRS/Agent/*.h` и
поддиректоријуме `backend/`, `config/` и `crypto/`.

Коме је намењена: ономе ко пише **платформског домаћина** — процес који држи
превоз и капију политике, а неутралном језгру препушта вођење картице. Ако
пишете *клијент* агента који већ ради, треба вам
[Изградња Qt клијента](/developer-guide/agent-client-qt/).

## Облик

```
        платформски домаћин (LibreLinux, LibreDarwin)
        држи: превоз · ауторизатора · упитник · разрешивач способности
                            │  ињектовани референцом
                            ▼
                        AgentCore
        држи: модел присуства · кешеве · праћење кључева · капију упита
              конфигурацију · мотор потписивања · ограничавач стопе
              менаџер закупа · распоређивач операција
```

`AgentCore` је **власничка агрегација са конструкторском ињекцијом**. Нема
`instance()`, нема лењо створеног глобала: домаћин га конструише једном, чим
његова четири позајмљена сарадника постоје, и држи га на месту. Тип се не може
ни копирати ни премештати, јер његови чланови чувају мутексе и радне нити.

```cpp
#include <LibreSCRS/Agent/AgentCore.h>

// resolver, transport, authorizer и prompter су у власништву домаћина и морају
// да надживе језгро.
LibreSCRS::Agent::AgentCore core{
    resolver, transport, authorizer, prompter,
    configFile,          // std::filesystem::path
    cacheRoot,           // std::filesystem::path
    resolveReaderCard,   // std::function<std::optional<ReaderCard>(const std::string&)>
    resolveCardKey};     // Pkcs11Broker::ResolveCardKeySeam
```

Све што језгро држи доступно је преко приступника који враћа референцу —
`core.presenceModel()`, `core.credentialCache()`, `core.objectRegistry()` — па
позадина поново узима из агрегације уместо да кешира сопствене копије.

### Зашто подела власништва није случајна

Чланови су декларисани у намерном унутрашњем редоследу зависности, па
конструкција иде од зависности навише, а деструкција строго
**позајмљивач пре позајмљеног**. То је инваријанта која картичном агенту највише
треба, и управо она се најлакше поквари премештањем једне декларације.

Вреди засебно рећи још једну инваријанту, јер објашњава тип који бисте иначе
сматрали чудним. Радња над приватним кључем или читање тече на радној нити по
читачу која уме да се блокира у позиву који нико не може да откаже: упит за
сагласност, преузимање задржане сесије, терминална радња на картици. Ако се
домаћин руши док та нит стоји, она надживи агрегацију која је држала њене
сараднике.

`CryptoWorkerContext` је одговор. Он у један дељени објекат скупља све што таква
нит сме да дотакне при одблокирању — упитник, капију упита, кешеве акредитива,
менаџер закупа, токен гашења. Свако затварање радне нити које може да надживи
агрегацију вредносно хвата **тај цео контекст**, па при одблокирању дира само
меморију коју сувласнички држи. Једно хватање уместо четири, и будући радни пут
је безбедан по конструкцији, а не по прегледу.

## Идентитет: три непрозирна токена

`Agent/Identity.h` дефинише три вредносна типа које језгро прослеђује и никада
не рашчлањује:

| Тип | Шта именује | Кује |
|---|---|---|
| `CallerToken` | једног повезаног клијента | позадина, из превоза |
| `ObjectId` | један читач, или једно убацивање картице | `PresenceModel` |
| `OperationId` | једну операцију у лету | `OperationManager::publish` |

Свако омотава вредност уз једнакост и потпуни поредак, и не нуди ништа друго.
`CallerToken` замењује оно што је раније било голо име на магистрали на **пет**
одвојених места — субјекат ауторизације, PKCS#11 позивалац, кључ закупа, кључ
ограничавача стопе и табела прекида везе — па позадина која клијенте
идентификује другачије мења једно пресликавање уместо пет.

`ObjectId` изричито **никада није отисак картице**; `0` је резервисана за
„ништа“. Позадина држи пресликавање `ObjectId`-а у путању на жици, и ниједна
компонента језгра путању не реконструише.

Зашто токен а не идентификатор процеса: `pid_t` се поново користи. Токен који
кује превоз имун је на поновну употребу док траје веза, што га чини безбедним
као субјекат ауторизације — домаћин га у тренутку провере разрешава у субјекат
процеса, закуцан преко pidfd-а или времена покретања.

## Четири позадинска интерфејса

Њих имплементира домаћин. То је цела платформска површина.

### `AgentTransport` — мембрана ка клијентима и њена диспечерска нит

```cpp
class AgentTransport {
public:
    virtual void publishReader(const ReaderState&) = 0;
    virtual void publishCard(const CardState&) = 0;
    virtual void withdraw(ObjectId) = 0;
    virtual void updateProperties(ObjectId reader, const PropertyDelta&) = 0;

    virtual void post(std::function<void()>) = 0;
    virtual void postAfter(std::chrono::microseconds, std::function<void()>) = 0;

    virtual void onClientDisconnect(std::function<void(CallerToken)>) = 0;
};
```

Три бриге које изгледају раздвојиво — објављивање објеката, слање на петљу
догађаја, и примећивање да је клијент отишао — намерно су један интерфејс. На
свакој платформи то је један кохерентан модел превоза и нити: D-Bus
`ObjectManager` плус sd-event плус `NameOwnerChanged` на Linux-у, XPC крајња
тачка плус dispatch плус поништење везе на macOS-у. Раздвајање би од домаћина
тражило да имплементира три погледа на један исти објекат.

`onClientDisconnect` је **адитиван**: сваки регистровани руковалац опали, редом
регистрације, при сваком прекиду везе. Продукција региструје два — аутоматско
отказивање из менаџера операција, па повлачење закупа из PKCS#11 посредника — и
тај редослед је део уговора.

### `Authorizer` — капија политике, са три исхода

```cpp
enum class AuthorizationOutcome : std::uint8_t { Granted, Denied, Undecided };

class Authorizer {
public:
    virtual AuthorizationOutcome authorize(std::string_view actionId,
                                           const CallerToken& caller) = 0;
};
```

Три стања, не два, и то је најважнији детаљ на овој страници. Клијенту коме је
речено „ниси овлашћен“ док власт није ни одговорила речено је нешто неистинито
о безбедносној одлуци. `Undecided` значи да **ништа није одлучено и ништа није
урађено** — недоступан сервис политике није одбијање, а ни истек времена док се
чека да човек одговори на упит није одбијање.

Идентификатори радњи су константе у истом заглављу, па се низови не могу
разићи између домаћиновог избора радње и његове имплементације `Authorizer`-а:

| Константа | Радња | Држање |
|---|---|---|
| `kActionConfigure` | измена подешавања потписивања | подразумевано дозволи |
| `kActionConfigureTrust` | измена подешавања поверења и жига | потврди идентитет |
| `kActionSign` | израда потписа | подразумевано дозволи, PIN је сагласност |
| `kActionPkcs11Login` | успостављање PKCS#11 закупа | подразумевано дозволи, PIN је сагласност |
| `kActionCredentialsManage` | промена или деблокада PIN-а | подразумевано дозволи, PIN је сагласност |

„Подразумевано дозволи“ није попустљивост: за те радње је PIN који корисник
управо куца сам доказ људског присуства, а други дијалог испред њега само би
научио људе да прокликћу кроз оба. Радња постоји да би политика сајта могла да
ограничи који клијенти смеју да траже, а ограничавач стопе кроти злоупотребу
испод подразумеваног. Подешавања поверења су изузетак јер мењају према чему се
потпис проверава.

У заглављу стоје и две имплементације: `AllowAllAuthorizer` за тестове и за
изричит режим без политике, и деградирана резерва која се користи када
платформски сервис ауторизације при покретању није доступан — она пада
**затворено** на радњи подизања поверења, а за оперативне радње задржава
подразумевано дозволи.

### `PrompterClientBase` — прикупљање тајни, без виђења превоза

```cpp
class PrompterClientBase {
public:
    virtual PromptResult requestPin(const PromptOptions&) = 0;
    virtual PromptResult requestCan(const PromptOptions&) = 0;
    virtual PromptResult requestMrz(const PromptOptions&) = 0;
    virtual void cancel(const std::string& promptId) noexcept;              // подразумевано ништа
    virtual PinChangePromptResult requestPinChange(const PromptOptions&);   // пада затворено
};
```

Тајна се враћа као `Secure::String` који се сам брише, никада као дескриптор
фајла, па језгро никада не види превоз који ју је донео.

Два правила уређују како овај интерфејс расте, и оба су носива:

- Раст иде **додавањем** виртуелне са безбедном подразумеваном имплементацијом —
  `requestPinChange` је таква, и њена подразумевана враћа `PromptStatus::Error`,
  па домаћин који није ожичио упит са две тајне пада затворено, а не тихо.
- Раст **никада** не иде преоптерећивањем постојећег имена. C++ тражење имена
  сакрива наслеђени скуп преоптерећења чим изведена класа декларише било који
  члан тог имена, па би сваки имплементатор запео на `-Woverloaded-virtual` —
  а спремиште домаћина гради са `-Werror`.

`cancel` прима идентификатор упита уместо да одбацује „тај упит“. Капија упита
кључана је по картици, па на екрану може бити више дијалога, а неадресирано
одбацивање затворило би онај који је на врху — врло често туђе картице.

### `CapabilityResolver`

Држи га улазна тачка процеса, а језгро га позајмљује; он одговара шта картица у
читачу уме. Документован је уз остатак машинерије присуства на страници
[Присуство и кеширање](/developer-guide/agent-presence-and-cache/).

## Логовање

`Agent/backend/Logging.h` је фасада без Qt-а, у простору имена
`LibreSCRS::Agent::log`:

```cpp
namespace LibreSCRS::Agent::log {
    enum class Level : std::uint8_t { Info, Warn, Error };
    using LogSink = std::function<void(Level, std::string_view line)>;

    void init(LogSink sink, std::string category = "rs.librescrs.agent");
    void resetForTest() noexcept;

    void info(std::string_view);      // такође warn, error
    template <class... Args> void infof(std::format_string<Args...>, Args&&...);
}
```

Ово је једини санкционисан глобал у процесу LibreAgent-а, и то санкционисан а
не трпљен: провлачење референце на логер све до `catch` блока унутар нити која
анкетира коштало би целу површину а не би донело ништа. `init` се ожичи једном
при једнонитном покретању, а `resetForTest()` је обавеза која уз глобал иде —
тест који убризга свој понор враћа уграђени, да следећи случај у истом бинарном
фајлу не буде погођен. Празан понор такође га враћа.

LibreMiddleware од 5.0 носи исти облик под `LibreSCRS::log`, до journald
префикса приоритета, па један дијагностички `grep` чита и слој домаћина и
middleware исто.

## Токени способности

`Agent/FeatureTokens.h` држи речник опционих способности агента — списак који се
дословно сервира на обе жице и који клијенти читају преко
`AgentClient::hasFeature()`. Намерно је само `std::`, доступан и из изградње у
којој је језгро потпуно искључено.

Занимљив је део правило које уз њега иде: **у низу сме да стоји само токен чија
површина за сервирање постоји.** Задатак који слети са новом површином премешта
свој токен из планираног списка у сервирани, у *истом комиту* који слеће са
површином. Способност се никада не оглашава пре него што постоји, јер клијент
који је затражи па добије неуспех нема начина да разликује „овде није подржано“
од „покварено је“.

## Криптографски механизми

`Agent/crypto/Mechanism.h` именује механизам који радња над кључем тражи, а
његове параметре држи као затворену али проширљиву унију:

```cpp
enum class Mechanism : std::uint8_t {
    RsaPkcs1Sign, RsaPssSign, EcdsaSign,          // приватни кључ, иза закупа
    RsaPkcs1Decrypt, RsaOaepDecrypt, EcdhDerive,
    RsaPkcs1Encrypt, RsaOaepEncrypt,              // јавни кључ, без сагласности
};
```

Два су данас ожичена (`RsaPkcs1Sign`, `RsaPkcs1Decrypt`, оба са празним
параметрима); остали су пројектовани као додаци. Замрзавање облика сада значи да
EC и RSA-PSS стижу као вредност набрајања плус грана параметара, а никада као
проширен потпис шава. Приметите да `RsaPssSign` намерно **није** на грани са
празним параметрима — PSS-у треба тројка хеш/MGF/дужина соли, и претварање да
није натерало би управо ону измену потписа коју овај дизајн избегава.
