`include/LibreSCRS/Agent/operations/` је највећа група у јавној површини
LibreAgent-а: **41 заглавље** на почетку 5.0 циклуса. У њој су саме картичне
операције, токови којима оне препуштају посао, шавови кроз које ти токови зову
картицу, и машинерија која све то распоређује и капије.

Ова страница је о тој машинерији. Ако вас занима клијентска страна једног од
ових позива, види
[Изградњу Qt клијента](/developer-guide/agent-client-qt/).

## Девет класа операција

Свака операција коју клијент може да затражи јесте једна класа изведена из
`OperationBase`, и свака је танак адаптер над током који ради посао:

| Операција | Шта ради |
|---|---|
| `ReadIdentityOperation` | чита идентитетске податке документа |
| `GetPhotoOperation` | чита фотографију; промашај кеша покреће идентитетски ток |
| `ReadCertificatesOperation` | чита сертификате са картице |
| `ReadTokenInfoOperation` | чита метаподатке токена — брат идентитетског читања, тачно као што је `CardPlugin::readTokenInfo` брат `readCard`-а |
| `SignOperation` | један AdES потпис |
| `SignBatchOperation` | више докумената под једним скупом параметара за целу серију |
| `ListCredentialsOperation` | исписује PIN акредитиве картице и њихово стање |
| `ManagePinOperation` | мења, деблокира или активира један PIN акредитив |
| `ActivateSigningKeyOperation` | проверава потписни PIN и активира кључ на картици |

Свака носи угнежђену структуру `Deps`: све што операцији треба, а даје јој
`OperationManager` при постављању у ред. Ниједна операција не посеже за
сарадником који јој није дат.

Вреди именовати образац. Класа операције не држи логику — она пресликава
захтев на ток, износи типизиране резултате како стижу, и завршава пресликаним
статусом. Ток испод ње (`SignFlow`, `IdentityReadFlow`, `CredentialListFlow`,
`PinChangeFlow`, `KeyActivationFlow`, `CertReadFlow`, `TokenInfoReadFlow`,
`RawCryptoFlow`, `BatchSignFlow`) јесте место где живи оркестрација, а ток
картицу зове само кроз ињектоване шавове — што цео тај слој чини тестабилним
без картице, без читача и без магистрале.

## Два дељена речника исхода

`FlowOutcome.h` декларише два набрајања која токови и шавови деле:

```cpp
enum class FlowOutcome { Ok, Cancelled, Error };

enum class SeamStatus {
    Ok, AuthFailed, ParseError, UnsupportedCard, CommunicationError, Cancelled,
};
```

Пет токова је враћало исти троструки исход а два шава исти шестоструки, свако
са својом копијом, истоветном до редоследа вредности. Разлог да се декларишу
једном није у уштеђеним линијама: у томе је да нова вредност сада стиже до
сваког `switch`-а **у време превођења**. `-Wswitch` именује оне који је не
обрађују, у изградњи која пада, уместо да приватну копију сваког тока пронађе
онај ко се сети.

Две разлике које речник намерно прави:

- `Cancelled` **није** грешка. Позивалац или држач сесије зауставио је посао, и
  о картици се не зна ништа лоше. Пријава отказивања као неуспеха је управо
  квар због кога ово раздвајање постоји.
- `SeamStatus` је шири од `FlowOutcome`-а јер је шав место где излазе картичина
  сопствена одбијања, а ток изнад мора да их разликује пре него што одлучи да
  ли да понови, да се поново пријави, или да одустане. `AuthFailed` и
  `CommunicationError` воде у различите следеће кораке; њихово сливање тај
  избор претвара у погађање.

Ток чији су исходи заиста његови задржава сопствено набрајање. Неколико их има,
и то нису ова два.

## Једна нит по читачу, једна сесија по нити

`OperationManager` држи по једну радну нит и ред по читачу. Свака нит држи по
један `CardSessionHolder`.

```
читач A ──▶ нит A ──▶ CardSessionHolder A ──▶ једна отворена CardSession
читач B ──▶ нит B ──▶ CardSessionHolder B ──▶ једна отворена CardSession
```

Држач лењо отвара једну сесију, поново је користи кроз позиве `acquire()`, и
листу кандидата-плагина разрешава једном по задржаној сесији. То поновно
коришћење није оптимизација — то је оно што омогућава да **PACE безбедни канал
преживи** из једне операције у следећу. Отварање по операцији поново би
изводило цело успостављање канала, а са њим и упит за акредитив.

Читач који стоји без посла проактивно се затвара после интервала мировања, да
устајали PACE канал и његова PC/SC ручка не би стајали заувек; следећи
`acquire()` је прозирно поново отвара. Држач се дира **само** на својој радној
нити: `enqueue` под мутексом нити утискује показивач у `Deps` операције, а нит
га разименује унутар `doWork()`-а.

Три ињектована шава чине ово тестабилним без PC/SC демона и без зидног сата:

```cpp
using SessionFactory   = std::function<std::expected<std::shared_ptr<CardSession>, OpenError>(const std::string& reader)>;
using CandidateResolver = std::function<CandidateList(std::span<const std::uint8_t> atr, CardSession&)>;
// плус steady Clock, дат при конструкцији
```

### Ограничење реда

```cpp
inline constexpr std::size_t kMaxQueuedOpsPerReader = 32;
struct QueueFull : std::runtime_error { /* ... */ };
```

Свака операција држи помоћне нити, па је неограничен ред неограничен број нити.
Ограничење претвара клијента који поплављује у именовано одбијање које позадина
пресликава у жичану грешку о ограничењу стопе, уместо у притисак на меморију.

`OperationManager` је неутралан према позадини: не држи ниједан тип превоза.
Прављење адаптера и пресликавање на жицу живе у платформској позадини.

## Која је ово картица? — `CardTypeArbitration`

Картица редовно одговара више од једног драјвера: породични драјвер плус један
или оба општа PKI драјвера, или — на картици коју ниједан породични не прихвата
— само та два општа. `CardTypeArbitration` бира низ типа картице за листу
кандидата задржане сесије, тако да свака површина која тип пријављује пријави
исти.

## Капија упита

`PromptSerializer` пропушта **највише један живи упит по картици**, и то „по
картици“ је цела поента.

Агент вози по једну нит по читачу, па два читача могу истовремено да покрену два
упита за акредитив — и то је намера. Ова капија је првобитно била на нивоу
целог агента, и управо то се показало као квар. Стражар по операцији наоружава
се при уласку у аутентификацију, *пре* него што нит стане у ред пред капију, па
неодговорен дијалог на једном читачу није само одлагао остале: чим би стражарев
буџет истекао, њихове операције су умирале са истеком времена, а њихове
странице са њима. Једна картица која чека CAN коштала је корисника свих осталих
картица у машини.

Кључање места по картици решава тачно то. Две различите картице пита се
истовремено. Две операције над истом картицом и даље се серијализују, а то је
случај коме то заиста треба — једна картица не може смислено да одговори на два
дијалога, а други дијалог за исту картицу увек је грешка или трка.

`PromptIdMinter` даје сваком упиту идентификатор, да отказивање може да именује
дијалог на који мисли; види уговор `cancel`-а на
[страници о језгру](/developer-guide/agent-architecture/).

## Ограничавач стопе

```cpp
static constexpr std::size_t kMaxPerWindow = 5;
static constexpr auto kWindow      = std::chrono::seconds{60};
static constexpr auto kBaseBackoff = std::chrono::seconds{2};
static constexpr auto kMaxBackoff  = std::chrono::seconds{60};
```

Уз држање „подразумевано дозволи“ и PIN као капију сагласности, неограничен
позивалац могао би да покрене пецање рефлексом: упит за упитом док корисник PIN
не откуца из навике. Ограничавач кроти покушаје по позиваоцу и претвара поплаву
у тврду грешку уместо у још један дијалог.

Један примерак ограничавача покрива и улаз за потписивање и улазе за измену
акредитива, па је поплава разливена преко та два ограничена као **један** буџет
по позиваоцу, а не два. Кључан је по токену позиваоца — имуном на поновну
употребу док траје веза, истом оном који користи ауторизатор — а сат прима
конструкторском ињекцијом, па тестови воде време детерминистички уместо да
спавају. Позивалац који остане испод границе враћа своје кашњење на нулу.

## Снимак мотора потписивања

`SigningEngineProvider` држи мотор потписивања који троши пут потписивања унутар
процеса, и издаје га као пар:

```cpp
struct EngineSnapshot {
    std::shared_ptr<LibreSCRS::Signing::SigningService> engine;
    std::string boundTsaUrl;   // празно када TSA није подешен (само B-B)
};
```

Оба поља хватају се под истом бравом, па потписивање у лету троши **сагласан**
пар: URL органа за временски жиг везан за мотор јесте онај који ће тај мотор
заиста контактирати, а не оно што жива конфигурација држи после истовремене
измене подешавања. Издавање мотора па засебно читање URL-а је квар
провери-па-употреби над метаподацима, а овај облик га спречава.

`engine` је нулти показивач када конфигурација поверења није могла да се
изгради; шав потписника нулти мотор пресликава у грешку мотора уместо да га
разименује.

## PIN као сагласност у сировом криптографском путу

`RawCryptoFlow` је пут којим иде потписивање или дешифровање PKCS#11 клијента.
Његова терминална радња прима прикупљени PIN као показивач, а два случаја су
уговор а не удобност:

- **није нулти** — радња мора да провери PIN на картици *пре* потписивања или
  дешифровања, држећи картицу кроз обоје, да би кључ са обавезним PIN-ом задржао
  проверено стање за радњу која одмах следи. Одбијање излази као неуспех
  аутентификације. Ово је прва радња у закупу, или прва после ранијег неуспеха.
- **нулти** — PIN је за овај задржани канал већ проверен.

Потписивање и дешифровање деле један потпис: усмерени кандидати и идентификатор
сертификата бирају кључ, а бајтови су улаз или шифрат.
